## 数据流

原采集工程执行器已经在每帧严格提交后计算并保留`gray`、`valid`和`residual_n`，且第八帧后用它们验证板端完整融合结果。第二步保留这一审计，复用其产物供后处理使用，不再重新算一套全图质量或按tile重算残差。

八帧完整残差是当前PC镜像审计的产物，不是新增PL回读。本方案以保留该工程审计为前提。未来若另行取消该审计，应重新评估证据来源并回退第一步按需访问，不能把两种互斥前提的节省同时计入。

```text
严格SDK：身份/参数/CRC/H1/H2
  → 原工程执行器的H2/质量与板端融合对照
  → 完整8帧、提交/RELEASE、OFF
  → from_executor：获取本组审计快照
  → seal：精确int16残差＋无损bit-pack质量＋来源回执
  → restore：来源/代码/数据哈希与本组原生输入核对
  → 解码实际PL R32，核对来源灰度、残差、有效性与unknown
  → 原冻结检测、弱段增强、复检和完整导出
```

## 绑定与拒绝条件

缓存绑定本组group/digest、八个完整帧身份、每帧实际曝光/增益/光向、ROI、mask、原片/载荷/原始metadata、R32及SDK来源。参考H2、质量、连接、解码和资格源码均有哈希核验。

缓存不是签名或安全证明。它用于受控本机流程中的完整性复用；不能把外来NPZ声明成已核验产物。首次生产者必须是严格SDK及工程对照，或明确标注的离线完整复核重建。第二种来源不能写成新实拍。

完整性错误明确拒绝，不覆盖旧缓存、不自动补拍。`pending`不算成功。快照拥有独立只读数组，不随下一组重用执行器、重置`_off_rows`而变化。

## 计时设计与界限

正式对照使用同一组已保存PL原片和R32、单线程OpenCV。每种方法三次，交替顺序，每次新建目标目录。对照为第一步缓存访问器；候选为本步交接复用。

起点是本组原生图、已核验的帧身份与审计数组已在RAM。离线重建这些采集审计数组在两个区间之外；真实采集工程原本已做这些计算。候选区间额外计入交接文件首次创建、写入、读取、代码及来源核验，不只挑已有缓存命中。两方法随后执行相同冻结计算、图片/数组/报告完整导出。

这个区间不包含物理采集、PL计算、FETCH、一次性导入、最初的原生身份快照构建及旧入口的native缓存IPC。接入GUI后还需完整区间实测，不能从历史整机时间减去本阶段差值来宣布整机加速。

`paired_01`出现一次518.964秒长墙钟停顿，其全部记录、原执行源码及正确性结果保留，但整批不用于性能结论。完整重跑`paired_02`同时记录墙钟和进程CPU时间；开始前固定单次大于120秒即保留整批并停止，不自动替换慢样本。本限制针对本次864×864固定原片，不能推广为所有图像的处理期限。
